# Tactical design

The tactical patterns are how a model is built inside one bounded context. Use them where the domain has real rules, above all in the core domain. In a simple supporting or generic part, a plain transaction script or CRUD can be the right answer.

## Entities

An **entity** is defined by its identity and continuity, not its attributes. Two orders with the same contents are still two orders.

- Choose how identity is made, deliberately: supplied by the user, generated by the application (for example a UUID), issued by the store, or assigned by another context. Generating it early, in the application or domain, makes events and references simpler.
- Give the identity its own type (an `OrderId`, not a bare string).
- Expose behaviour named in the language, not setters. `order.cancel(reason)` keeps the rule in one place; `order.setStatus(CANCELLED)` scatters it.
- Validate at three levels: each attribute (usually by making it a value object), the whole object, and, where needed, a composition of objects (often in a domain service or specification).

## Value objects

A **value object** measures, quantifies or describes something, and has no identity of its own: two equal amounts of money are interchangeable.

- Immutable. An operation returns a new value instead of changing the old one.
- Equal when all its attributes are equal.
- Self-validating: it can't be created in an invalid state.
- Side-effect-free behaviour: `price.withDiscount(rate)` computes; it doesn't save anything.
- Prefer value objects over primitives and over entities. Model a concept as an entity only when its identity really matters over time. Money, date ranges, addresses, quantities, email addresses and statuses are usually values.
- Persist them as part of their owning entity (columns, an embedded document or a serialised field), not as tables with their own identity, unless storage forces it.

## Aggregates

An **aggregate** is a cluster of entities and value objects treated as one unit for consistency, with one entity as its **root**. Outside code refers only to the root. The aggregate boundary is the transaction boundary.

Vernon's four rules for aggregate design:

1. **Model true invariants in consistency boundaries.** An invariant is a rule that must always be true, immediately, after every transaction. Put inside one aggregate only what must be consistent with it at once. Group by invariant, not by "these things are related" or "the screen shows them together".
2. **Design small aggregates.** Most aggregates are a root entity plus value objects. Large clusters cause contention between users, slow loading and transactions that fail for no domain reason. Start small and grow only when a true invariant demands it.
3. **Reference other aggregates by identity.** Hold a `ProductId`, not a `Product`. That keeps aggregates small, makes the boundary visible, lets them be stored separately, and stops one transaction quietly reaching into several.
4. **Use eventual consistency outside the boundary.** When a rule spans aggregates, change one in the transaction, publish a domain event, and update the others in their own transactions. Ask the experts how soon it must be true: the answer is often "within seconds" or "by the end of the day", not "atomically".

Reasons to break a rule, rarely and on purpose: the user interface genuinely needs one action to create several aggregates at once, there's no messaging or background processing available, or a global transaction is truly required. Write the reason down when you do.

More on aggregates:

- **One aggregate per transaction.** An application service that changes two aggregates in one transaction is the usual sign a rule is in the wrong place or a boundary is wrong.
- **Ask who's responsible.** If the rule is "this user's change must update that other aggregate", the update is often that other aggregate's job, triggered by an event.
- **Protect the root.** Changes go through the root's methods. Nothing outside holds a reference to an inner entity.
- **Optimistic concurrency.** Give the aggregate a version and fail a stale write, rather than locking.
- **Tell, don't ask; and keep the law of Demeter.** Callers tell the root what to do instead of reaching inside it.
- **Don't inject repositories or services into an aggregate.** Pass what a method needs as arguments, or move the coordination to a domain service.

## Domain events

A **domain event** records something that happened that the experts care about, named in the past tense in the language: `OrderPlaced`, `PaymentDeclined`, `BacklogItemCommitted`.

- Listen for the phrases "when…", "if that happens…", "notify…" and "as a result…": they often mark an event.
- An event is immutable and carries what a subscriber needs: the identities involved, the relevant values and when it occurred. Keep it small, but complete enough that subscribers don't have to call back.
- The aggregate raises it as part of its behaviour. The application service saves the aggregate and the event together, then publishes.
- **Inside the context**, a subscriber updates another aggregate in its own transaction, or triggers a side effect.
- **Across contexts**, events are the default integration. To publish reliably, store events in the same transaction as the aggregate (an event store or outbox table) and forward them afterwards, so a crash can't lose one or publish one that never happened.
- Subscribers must be **idempotent**: they may see the same event more than once, and in a different order from how it was raised. De-duplicate by event identity, or make the change naturally repeatable.
- Events are also the raw material for audit, integration and, where it's earned, event sourcing.

## Repositories

A **repository** gives the illusion of an in-memory collection of aggregates. There's one per aggregate type, never per table or entity.

- The interface is in the domain layer, in the language (`ordersAwaitingShipment()`), and the implementation is an adapter in infrastructure.
- **Collection-oriented** repositories behave like a set (`add`, and changes are tracked); **persistence-oriented** ones need an explicit `save`. Follow what the repository's persistence already does.
- Load and save whole aggregates. Don't return or update parts of them.
- Transactions are controlled by the application service, not by the repository or the domain.
- Queries that serve screens, not behaviour, don't belong on the repository; see query models in `architecture.md`.

## Domain services

A **domain service** holds a domain operation that doesn't naturally belong to one entity or value object, typically because it spans several aggregates or needs something outside the model, such as a policy or calculation.

- Stateless, named in the language (`TransferService`, `PricingPolicy`), with domain types in and out.
- Not a place to dump logic. Try the entity or value object first; an over-used service leaves an anaemic model.
- Different from an application service: a domain service holds business rules; an application service coordinates a use case and holds none.

## Factories

A **factory** creates a complex aggregate, or one aggregate from another, so the creation rules aren't scattered.

- Often a method on an existing aggregate root (`calendar.scheduleEntry(...)`), which also keeps the language natural, or a domain service when creation needs outside translation.
- It produces a whole, valid aggregate, or fails.

## Modules

Group domain code into **modules** named after domain concepts, inside the bounded context, not after technical kinds. `orders/` and `pricing/` tell a reader about the business; `entities/` and `services/` don't. Keep coupling between modules low, and don't confuse a module with a bounded context: a context contains modules.

## Tactical questions

- Is this an entity or a value? If identity doesn't matter, make it a value object.
- What invariant must be true immediately, and which single aggregate owns it?
- Does this transaction change more than one aggregate? If so, which event should carry the rest?
- Does this behaviour belong on the root, a value object or a domain service?
